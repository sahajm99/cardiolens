## Problem Statement

The UNT CSCE 5320 Group 6 project (Spring 2025) asked how lifestyle, demographic and
health factors relate to self-reported heart disease in the CDC BRFSS 2020 sample
(319,795 adults, 18 columns). The course deliverable was a Tableau workbook, a
matplotlib/seaborn EDA notebook, two slide decks and a Netlify page with D3 charts.
None of it survives as something a hiring manager can open, and the numbers were
counts without confidence intervals or adjustment for age.

CardioLens turns that work into a live, public, story-shaped analysis site: every chart
is a claim with n and a 95% CI, the risk factors are shown adjusted for each other
(logistic regression), and the limits of the data are stated on the page rather than
in an appendix.

## What Makes This Cool

- Every chart title is a sentence a stranger can repeat. "Smokers report 1.6x the
  prevalence of non-smokers" rather than "Heart Disease by Smoking".
- Crude vs adjusted, side by side. Age explains most of the raw gap for several
  factors. The adjusted-odds-ratio chart shows what survives when age, sex, BMI and
  comorbidities are held constant. That is the "whoa" moment the course version never had.
- The site never touches the CSV. A Python pipeline turns 25 MB of rows into a few
  small JSON aggregates, so the page loads in under 3 seconds on a phone.
- Honesty as a design feature. Wilson intervals on every proportion, a class-imbalance
  note, a self-report note, and a closing section titled "What this data cannot tell you".

## Constraints

- Source data is read-only and lives in the UNT course folder; a copy is committed under
  `data/raw/` with `SOURCE.md`.
- No State column in the 2020 file, so no geographic analysis. Stated on the page.
- Stack is fixed: Python 3.12 + pandas + statsmodels + pytest for the pipeline;
  Vite + TypeScript + Plotly.js for the site (D3 only where Plotly cannot express it);
  GitHub Pages via Actions; no CDN.
- Each JSON output under 200 KB. Never ship raw rows to the browser.
- Colourblind-safe palette, alt text per chart, keyboard navigation, light and dark.
- Phase 2 synthetic heart_prediction_dataset.csv is out of scope (different, synthetic
  data; would muddy the story).

## Premises

1. The course question list is a good skeleton for a story and does not need replacing,
   only reordering into hook, risk factors, interactions, equity, limits.
2. Aggregates plus a logistic model are enough to answer every question; no browser-side
   computation over raw rows is required.
3. A single long-scroll page with a sticky section nav reads better for a portfolio piece
   than a tabbed dashboard.
4. Pages deploy from a build artifact produced in CI, so the repo never carries `dist/`.

## Approaches Considered

### Approach A: Minimal viable (static Plotly page from hand-exported JSON)
Summary: export aggregates once from a notebook, paste into a static page.
Effort: S. Risk: Med (not reproducible, numbers drift from notebook).
Pros: fastest to a URL. Cons: fails definition-of-done items 5, 6, 7.

### Approach B: Ideal architecture (pipeline package, JSON contract, typed site)
Summary: `pipeline/` is a Python package with one function per aggregate, each with a
pytest test; `python -m pipeline` writes `site/public/data/*.json`; the site has a
TypeScript type per JSON file and one chart module per section; CI runs pipeline, tests,
type-check, build, and deploys Pages.
Effort: M. Risk: Low.
Pros: reproducible, testable, every number on the page traceable to a function.
Cons: more files; needs a clear JSON contract up front.

### Approach C: Lateral (publish the analysis notebook itself as the site)
Summary: Quarto or Jupyter Book renders the notebook as the site.
Effort: M. Risk: Med.
Pros: narrative and code in one place. Cons: violates the fixed stack, harder to make
it not look like a notebook, weaker mobile story.

## Recommended Approach

Approach B. It is the only one that satisfies all eight definition-of-done items, and
the JSON contract is the natural seam between the Python and TypeScript halves.

### Story structure (page sections)

1. Hook: one big number. 8.6% of 319,795 adults report heart disease. Age curve
   from under 1% (18-24) to about 23% (80+). Stat tiles plus the age prevalence chart.
2. Risk factors: smoking, stroke, diabetes, difficulty walking, kidney disease,
   physical inactivity, general health, sex. Crude prevalence with Wilson CIs, then the
   adjusted-odds-ratio forest chart from logistic regression.
3. Interactions: BMI x sleep x mental health; age x sleep; BMI vs stroke and HD;
   sex x age; smoking x age.
4. Equity lens: race vs HD (crude and age-standardised); race x stroke x HD;
   BMI / sleep / activity by race; race vs general health.
5. What this does not show: cross-sectional, self-report, class imbalance, no State
   column, survivorship, BRFSS weighting not applied.

### Interaction rules

- Hover tooltips show n, prevalence, CI. No cross-filtering; each chart answers its own
  question and the page is the story.
- Charts 3 and 6 get a small control (factor picker / metric toggle) implemented as native
  `<select>` or `<button>` groups for keyboard access.
- Theme follows `prefers-color-scheme` with a manual toggle persisted in localStorage.

## What I noticed about how you think
